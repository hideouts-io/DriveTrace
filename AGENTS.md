# DriveTrace repository instructions

## Project-local delivery defaults

- Before making changes, read `WORKSPACE.md` when present, this `AGENTS.md`, any applicable `AGENTS.override.md`, `TODO.md`, project documentation, and the latest DriveTrace checkpoint. Verify the canonical checkout, Git root, current branch, `HEAD`, remote, upstream, attached worktrees, open pull requests, and staged, unstaged, and untracked files. Preserve unrelated work. If no `WORKSPACE.md` or override exists in the applicable scope, record that fact rather than inventing one.
- Do not start adapters, dependencies, installers, packaging, or CI work while an actionable TODO remains. Continue the accepted earliest TODO/milestone in its established order; do not create a replacement roadmap or duplicate backlog.
- Standing authorization for this project covers the normal GitHub delivery of work implemented and verified in the current task: stage reviewed task files or hunks, create focused `codex/` branches and conventional commits, push ordinary non-force updates to the verified task branch, create or update a review pull request, mark a draft pull request ready after implementation and required checks complete, and make reasonable CI fixes needed for that pull request.
- Use a pull request by default for source, behavior, packaging, workflow, dependency, security-sensitive, or substantial multi-file changes. A direct push is acceptable only on the correct non-protected task branch when it follows repository practice and does not bypass required review or branch protection.
- Before every commit or push, reconfirm the canonical repository, branch, remote URL, upstream, `HEAD`, outgoing diff, and preservation of unrelated staged, unstaged, and untracked work. Stage explicit reviewed paths or hunks only; never use `git add .`, `git add -A`, or `git commit -a` in a dirty canonical checkout. Inspect the complete staged diff and check for credentials, private evidence, device identifiers, personal data, local absolute paths, backups, logs, downloaded indicators, build caches, and private test artifacts. Run applicable tests, linting, documentation, packaging, and native UI checks; review the final diff for regressions, security issues, scope drift, and generated-file mistakes.
- Fetch and inspect the verified remote before integrating upstream changes; never use a blind pull. Push only the intended branch and verify that the remote revision matches the expected commit. Inspect resulting GitHub checks and repair failures without weakening tests, assertions, security controls, or required gates.
- If the canonical checkout contains overlapping or conflicting user work, preserve it and use a suitable existing review worktree or create a focused worktree from the correct committed base. Do not reset, clean, stash, discard, overwrite, or silently include unrelated changes.
- This authorization does not cover merging pull requests, force-pushing or rewriting published history, deleting remote branches, creating tags or releases, publishing release artifacts, deploying an application or website, approving protected environments or publication jobs, changing branch protection/visibility/permissions/secrets/Actions settings, installing or broadening GitHub App access, or sending unrelated external messages. Ask for separate authorization before those operations.

## Project continuity defaults

- At the beginning of each work session, load the latest project memory and checkpoint. At least hourly during active work, and again before ending or pausing, update the existing project checkpoint or continuity location with the objective and scope, canonical checkout/worktree, branch/`HEAD`/remote/PR, relevant Git state, intentional changes, completed and remaining TODOs, implementation decisions, exact test/build/CI/native outcomes, bundle and native-window evidence when applicable, investigated failures, blockers, and next safe action. Do not create duplicate planning documents or store credentials, secrets, signing material, device identifiers, raw backups, private logs, downloaded threat intelligence, personal information, or large command output.
- Keep implementation, commit/push/PR, merge, release/publication, settings/permission changes, destructive actions, and device operations as separate authorization boundaries. A successful pull request and passing CI do not authorize a merge, release, deployment, or publication.
- Report what actually changed and ran. Distinguish passed, failed, pending, skipped, blocked, inferred, and unverified results; keep source builds, synthetic tests, native UI, real-account behavior, hosted CI, signing, notarization, and distribution evidence separate.

## DriveTrace technical constraints

- Preserve the native SwiftPM app, system SQLite integration, bundle identity, Keychain service, and existing storage namespaces.
- Run the source build and tests in `.github/workflows/ci.yml` for source changes. Keep the `Swift build and tests` check emitted for every PR. Local packaging remains owned by `script/build.sh` and `script/verify_bundle.sh`.
- Keep native CI and Swift CodeQL on explicit Xcode 26.6 for the UserNotifications concurrency contract. Verify the actual toolchain and all production sources. Keep Swift and the CSQLite header in the explicit CodeQL builds. Confirm successful analysis for each intended language at the reviewed revision; an enabled setup or successful workflow alone does not establish coverage.
- Keep OAuth client files, tokens, real Drive caches, private exports, and account screenshots outside Git and CI artifacts. Use the existing synthetic tests without connecting a real Google account.
- Report native UI and real-account validation separately from source builds and synthetic tests. Local ad hoc packaging does not establish Developer ID signing, notarization, or distribution readiness.
